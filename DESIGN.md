# Design & Architecture

## Overview
```
Browser chat (text + Web Speech voice in/out)
        │  POST /api/chat
FastAPI ── Agent ──► LLM (OpenAI-compatible, tool calling)   [if OPENAI_API_KEY set]
              │         └─ else: deterministic intent router + templated answers
              ▼
          tools.py  (rank / compare / long_haul / unmet_demand / live_status / methodology)
              ▼
          scoring.py  (pure, deterministic)  ◄── data_sources.py
                                                  ├─ OurAirports CSV  (coords, runways)      public, cached
                                                  ├─ FAA NAS Status API (live delays)         public, live
                                                  ├─ OpenFlights routes.dat (route network)   public, cached
                                                  └─ seed_airports.csv (enplanements, ops, constraints)
```

## Where AI is used (and not)
- **LLM**: understands the question, picks tools / arguments (region, airports, thresholds, weight overrides),
  maintains conversational context, and writes the explanation. System prompt forbids inventing numbers.
- **Not LLM**: every number. Scores, rankings, distances and percentages come from `scoring.py`. Tools return
  assumptions/caveats alongside results so the LLM must surface them.
- Without an API key an offline router handles the four sample question types and simple follow-ups, so the
  project runs and tests with zero credentials (and demonstrates the scoring is independent of the LLM).

## Scoring methodology
All components are **percentile ranks (0-100) within the 41-airport peer set**, so they are unitless and robust to outliers.

**Opportunity score** (terminal expansion profitability proxy) = weighted sum:

| Component | Weight | Definition | Rationale |
|---|---|---|---|
| growth | 25% | CAGR of enplanements 2019→2023 | Demand momentum |
| pressure | 30% | 0.6·pct(ops/runway) + 0.4·pct(enplanements/runway) | Demand vs physical capacity |
| scale | 20% | pct(log enplanements) | Revenue base to amortize capex |
| delay | 10% | Live FAA delay/GDP/ground-stop score | Current stress (noisy snapshot) |
| feasibility | 15% | 100·(1 − constraint) | Curfews, caps, slot controls, site limits block returns |

Weights are overridable per query. If the FAA feed is down, the delay weight is dropped and others renormalised (reported).

**Congestion index** = 0.8·pressure + 0.2·live delay score. **Unmet-demand index** (proxy) =
0.40·pressure + 0.30·constraint·100 + 0.15·growth + 0.15·live delay; the "why" is generated by rules over the same
components (e.g. runway-constrained, below-2019 recovery ⇒ partly recoverable without capacity).
**Long-haul share** = share of airline routes with great-circle distance ≥ 1500 mi (configurable).

## Key tradeoffs & Source Evaluation
- **Public data limits**: BTS T-100/On-Time and FAA ATADS have no public keyless REST API, and OpenSky historical endpoints require authenticated enterprise accounts. The prototype combines lightweight keyless public feeds with a curated seed dataset, making the provenance and limitations of each data source fully transparent.
- **Data Source Assessment**:
  1. *OurAirports (`airports.csv`)*: Retains `iso_region` (e.g. `US-MA`), `municipality`, and `scheduled_service`. Deduplication prioritizes `large_airport > medium_airport > small_airport` to avoid collision with seaplane bases or minor airfields sharing local codes.
  2. *OurAirports (`runways.csv`)*: Runways measure physical airside layout, which is retained as an airside feasibility constraint/context rather than conflated with terminal processing capacity.
  3. *FAA NAS Status API*: Captures live operational programs (Ground Stops, GDPs, Arrival/Departure delays). Preserves multi-event alerts and avoids fabricating artificial numeric delay minutes for qualitative events like Ground Stops (which stop departures at origin). Used as a live stress indicator, while long-term investment models should rely on BTS historical on-time data.
  4. *OpenFlights (`routes.dat`)*: Historical snapshot (~2014) filtered to direct nonstop routes (`stops == 0`). Measures network breadth rather than flight frequency or passenger seats. In production, this should be superseded by BTS T-100 Segment data.
- **Unmet Demand Estimation**:
  Unmet demand is not directly observable in any public aviation dataset (public records report *realized* flights and passengers, not turned-away passengers or unfiled airline schedules). Our architecture provides a defensible multi-signal proxy (capacity pressure, physical/legal constraints, demand growth) while explicitly communicating the boundary between measured traffic and unobservable latent demand.

## Uncertainty & scoping communicated
Every tool result carries `scope`/`note`/`caveats`; the system prompt requires them in answers; out-of-universe airports
return an error rather than a guess.

## Recommended Next Sources for Production
1. **BTS T-100 Domestic/International Segment**: Scheduled vs performed departures, seat capacity, passengers transported, and true segment distance. Replaces route counts with actual capacity and passenger volume.
2. **BTS Airline On-Time Reporting**: 12-month historical delay, cancellation, and taxi-time distributions to measure persistent congestion without relying on point-in-time FAA NAS snapshots.
3. **FAA Terminal Area Forecast (TAF)**: Long-term FAA official forecast of enplanements and operations to assess future growth trajectories.
4. **Airport Master Plans & Capital Improvement Plans (ACIP)**: Gate count, peak-hour gate utilization, terminal square footage per passenger, and existing capital commitments.
